# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/).

## [Unreleased (0.6.0)]

### Added
- **Standalone `.cs` file support** — any tool's `solutionPath` now also accepts a single `.cs` file (a .NET 10 "file-based program" you'd launch with `dotnet run file.cs`), with or without `#:` directives (`#:package`, `#:project`, `#:sdk`, `#:property`). The SDK itself turns the file into a project: the server calls `dotnet run-api` (the same mechanism Roslyn's own language server uses) to get the exact virtual project, then loads it through the normal MSBuildWorkspace pipeline. A standalone file therefore behaves like a real project — it gets the SDK's **default analyzers and source generators** (so `[GeneratedRegex]` and friends work even with no directives), `#:package` references resolve, `#:project` references load as **source** projects (go-to-definition / find-references cross into them), and diagnostics match `dotnet build`/`dotnet run`. Editing a file's `#:` directives rebuilds the project; editing only its code updates incrementally. The project is materialized in place — at `<entry>.cs.csproj` in the entry file's directory, exactly where the SDK/LSP put it — so the entire repo MSBuild context (`Directory.Build.props`/`.targets`, `global.json`, `NuGet.config`, `Directory.Packages.props`) is honored by construction, not approximated. That wrapper is git-ignored (best-effort, via the repo's local `.git/info/exclude`, so no tracked `.gitignore` is touched), is deleted immediately once loaded, and is the only thing written into your tree — build output goes to the SDK's own artifacts location, same as `dotnet run`. If the SDK can't produce a project (e.g. `dotnet run-api` unavailable) the server falls back to a framework-only in-memory workspace so the file still loads.
- **Workspace caching** — a loaded solution is now cached (default 20-minute idle TTL) and reused across tool calls instead of paying a full MSBuild load every time. Edits to tracked files are applied incrementally as in-place document text updates; project-file and Razor changes still trigger a reload.
- **Incremental document reconciliation** — newly added, removed, or renamed `.cs` files are picked up by re-evaluating just the affected project with MSBuild and applying the difference, instead of reloading the whole solution. MSBuild — not a path guess — decides which files belong to the project (globs, `<Compile Remove>`, links).
- **Analyzer & source-generator shadow-copy loader** — analyzer/generator assemblies load from a private per-process temp copy (the way Visual Studio does), so a concurrent `dotnet build` is no longer blocked by build output the server holds open (MSB3026/MSB3027/MSB3021). Each analyzer directory gets its own isolated loader, dependencies resolve to the highest matching version, and stale copies are cleaned up during the session. Opt out with `ROSLYNMCP_DISABLE_ANALYZER_SHADOW_COPY=1`.
- **HTTP transport mode** — the server can run over HTTP in addition to stdio.
- **Razor / Blazor diagnostics** — `get_diagnostics` now accepts `.razor` and `.cshtml` files and reports RZ diagnostics against the source file (not the generated `.g.cs`). When the Razor generator can't be loaded it reports an `RMCP0001` info diagnostic, and a generator that throws at runtime reports `RMCP0002`, so an unexpectedly empty result is explained instead of silent.
- **Symbol-search candidates on build errors** — symbol search responds with possible matching candidates when the project has build errors instead of failing outright.
- **Wrong-column recovery** — when a supplied `line`/`column` lands on the wrong identifier (e.g. `TimeSpan` instead of `FromSeconds` in `TimeSpan.FromSeconds`) but a `symbolName` was given, the tool scans the line for a unique match, retries there, and reports the corrected location.
- **Claude Code plugin definition** plus a `/setup` slash command that guides installation of the `roslyn-mcp` .NET global tool after the plugin is cloned.
- Local install scripts [install-local.ps1](./install-local.ps1) for the `roslyn-mcp` dev tool and `roslyn-cli`.
- **`get_diagnostics` scoping and filters** — `projectPath` compiles and reports only one project of the solution (all of its target frameworks), so the call no longer pays for the whole solution; `diagnosticIds` / `excludeDiagnosticIds` keep or drop IDs (case-insensitive, the exclusion wins); `messageFilter` keeps diagnostics whose message contains a case-insensitive substring; `maxResults` caps the list, with `totalCount` counting every match and a new `truncated` flag. The filters cover the synthetic `RMCP0001`/`RMCP0002` entries and generator-reported (e.g. `RZ`) diagnostics as well, `projectPath` keeps only the `RMCP0001` load issues of its own project, and everything combines with `sourceFile` and `severityFilter`.
- **`search_symbols` matching and scoping** — `exactMatch` matches the whole symbol name instead of a substring, and `caseSensitive` matches the query case-sensitively (both default to `false`, which keeps the case-insensitive substring match). `projectPath` searches and compiles only one project of the solution (all of its target frameworks); `namespaceFilter` keeps symbols declared in a namespace or one nested in it, by whole segments and case-insensitively (`App.Core` matches `App.Core.X` but not `App.CoreUtils`); `sourceFile` keeps symbols declared in one file, a partial type when any of its declarations is there, and reports that declaration's location. `totalCount` now counts a symbol compiled for several target frameworks once, also past `maxResults`.
- **`find_references` scoping** — `includeDeclaration: false` returns usages only (the default `true` keeps the declarations); `referenceFile` keeps references located in one file and `projectPath` those in one project of the solution (all of its target frameworks). Both also narrow the documents Roslyn searches, so a scoped call on a widely used symbol does less work. The filters run before `maxResults`, so `totalCount` and `truncated` describe the filtered set.
- **`find_callers` scoping** — `callerFile` keeps the call sites located in one file and `projectPath` those in one project of the solution (all of its target frameworks), applied before `maxResults` and narrowing the documents searched, like `find_references`' `referenceFile` / `projectPath`.
- **Direct descendants only** — `find_implementations` and `get_type_hierarchy` take `transitive` (default `true`); `false` leaves out what is reached only indirectly. For a class that is Roslyn's non-transitive derived-class search; for an interface, the types (and, in `get_type_hierarchy`, interfaces) that list it in their own base list, so a subclass of an implementer or a type implementing it through a derived interface is left out; for an interface member, the implementations of those direct implementers, an inherited one included. `get_type_hierarchy` also takes `maxResults` for its derived types and reports `derivedTypesTotalCount` and `derivedTypesTruncated`.
- **`get_document_outline` depth, filters and cap** — `maxDepth` limits how deep the outline goes, with namespaces not counting (`1` = top-level types only, `2` = plus their members); `kindFilter` (the `search_symbols` kind names, a constructor counting as `Method` and an enum member as `Constant`) and `nameFilter` (case-insensitive substring) keep the matching entries together with the namespaces and types containing them, so the tree stays navigable; `maxResults` caps the entries, counted depth-first with parents before children, and the result gains a `truncated` flag next to `totalCount`, which counts the filtered outline.
- **`get_symbol_info` member filters** — for a type, `kindFilter` (the `search_symbols` kind names), `nameFilter` (case-insensitive substring) and `accessibilityFilter` (exact declared accessibility: `public`, `internal`, `protected`, `private`, `protected internal`, `private protected`) narrow the listed members, and `maxResults` caps them; the result reports `membersTotalCount` and `membersTruncated`. For any other symbol the options are ignored.
- **`--version` / `-v`** for `roslyn-mcp` and `roslyn-cli`: prints the version (`0.6.0`; a build installed by `install-local.ps1` prints `0.6.0-local`) and exits with 0 before anything else starts, so the server writes no log entry, registers no MSBuild and puts nothing else on stdout. It is the assembly's informational version without the `+<commit>` build metadata, the same string the MCP `initialize` response now reports as `serverInfo.version` (which used the assembly version and so never showed a `-local` suffix). `roslyn-cli` takes the flag as its first argument only, since later arguments can be option values.
- **`change_return_type`** (new tool; 42 tools in total): changes the return type of a method, or the type of a property or indexer (`memberName` `this`), on the same override / implementation family as `change_signature`, with the same refusals. Only the declarations change; return statements, bodies and callers are not rewritten. Instead the result lists under the new `warnings` field the compiler errors the change introduces in the affected documents (the declaring files, the files declaring the members' types, and every file that references a member), each as `path(line,column): error CSxxxx: message`; errors that were there before are not listed. `void` is allowed in both directions for methods (the missing or superfluous `return`s show up among the warnings) and refused for properties and indexers; a `ref` return stays one. `newType` is resolved where the member is declared and written in each member's context like `change_signature`'s types: simplified to what the file's usings allow, `?` on reference types only where nullable annotations are enabled, `T` translated through generic base types. Files keep their encoding and line endings. `preview` returns each declaration's type before and after, plus the warnings. `RefactoringResult` gains the optional `warnings` (omitted when empty), which the CLI's text output lists.
- **`find_unused_symbols`** (new tool; 43 tools in total): lists the types and members declared in source that nothing references outside their own declaration, so a recursive call, a type naming itself or a symbol's own documentation comment is no use, while a `nameof`, a `cref` elsewhere and a reference from source-generated code are. A type counts as used when it or one of its members or nested types is referenced from outside the type (a static class whose extension methods are called is used); the members and nested types of a type that is listed are not listed separately (deleting the type removes them, and `totalCount` counts them the same way), unless `kindFilter` leaves the types out. By default only symbols not visible outside their assembly are reported, judged by effective accessibility (a public member of an internal type is internal); `includePublic` adds public ones and protected ones in types that can be derived from. Left out because something other than a reference uses them: overrides, interface implementations (implicit, explicit, or for a derived class), the entry point and its types, operators and conversions, finalizers, static and parameterless constructors, primary constructors and positional record properties, partial methods and properties, `extern` members, enum members, and declarations in generated files (`obj/`, `*.g.cs`, `<auto-generated>` headers). Symbols with attributes, types containing them, and fields of `[StructLayout]`, `[InlineArray]` or `[Serializable]` types are left out unless `includeAttributed` is set; attributes that only inform the compiler or debugger (`System.Diagnostics.CodeAnalysis`, `[Obsolete]`, `[MethodImpl]`, `[Debugger*]`) don't count. `projectPath` and `sourceFile` choose where the reported symbols are declared, `kindFilter` their kind, `maxResults` (default 100) caps the list after ordering by file, line and column, with `totalCount` and `truncated`; `symbolsChecked` says how many symbols were searched. A private symbol is searched only in the declarations of the type it is private to, a file-local one in its file, an internal one in its project and the projects its `InternalsVisibleTo` names, in parallel; a symbol of a multi-targeted project is reported only when unused in every target framework. Each entry has name, fully qualified name, kind, containing type, declared accessibility, file, line and column. The results are candidates: reflection, serialization, XAML/Razor bindings, string-based lookups and other assemblies are invisible. On this repository (`RoslynMcp.sln`, about 1,600 symbols checked) the search takes about 2.2 s after a cold 2.6 s load and 0.1 to 0.2 s warm.
- **`safe_delete`** (new tool; 44 tools in total): deletes the declaration of a type or member only when nothing outside it references it, and otherwise fails with `SymbolStillReferenced` (3120), whose message names the first references and whose `details` carry `totalCount`, `crefCount` and the first 20 references (`file`, `line`, `column`, `kind`, `snippet`). Every reference Roslyn finds counts, `nameof` included; a documentation-comment `cref` counts too and is reported with kind `cref`; a derived class's constructor that calls a base constructor without `: base(...)` is reported with kind `implicit`. References inside the deleted declaration (recursion, a type naming itself, its own doc comment) don't count, and a type is referenced through its members and nested types as well (a called extension method keeps its class). The symbol is found like `rename_symbol` does it (`symbolName`, optionally `line` / `column`, also from a usage); a constructor or finalizer is named by its type's name together with its line, an operator by its metadata name. Refused with `MemberInFamily` (3121), naming the related members: overrides, interface implementations (implicit and explicit) and members that are overridden or implemented. Refused with `CannotDelete` (3122): the entry point, static constructors, finalizers, implicit conversions, primary constructors, positional record properties, an enum member whose deletion would change the values of the members after it, and symbols declared implicitly, in metadata or in generated code. Every partial part of a type is removed, of `int a, b;` only the variable (an event field likewise), and the documentation and plain comments directly above a declaration go with it while a blank line or a `#region` above stops them; one blank line next to the declaration goes too, so blank lines neither pile up nor end up right after `{` or before `}`. A file left with nothing but usings, namespaces and comments (a type that was alone in it) is deleted and leaves the workspace, the same way a deletion on disk is reconciled; a file with global usings or assembly attributes stays. Files keep their encoding and line endings. Compiler errors the deletion still introduces in the touched files (for a constructor, also in the files using its type and its derived classes, e.g. a `new()` constraint) are returned as `warnings`, together with a note when a class loses its last constructor. `preview` lists each removal (first line, line range) or file deletion, with the warnings.
- **`rename_namespace`** (new tool; 45 tools in total): renames a namespace declared in source (`oldNamespace`, fully qualified) to `newNamespace` across the solution, every sub-namespace with it by prefix (`Old.Sub.Inner` becomes `New.Sub.Inner`); the depth may change. It rewrites block-scoped and file-scoped declarations, nested and dotted ones, and every name that refers to the namespace in code and in documentation-comment crefs: `using`, `global using`, `using static` and using-alias directives, qualified names and `global::` names. A fully qualified name gets the new name, a `global::` name keeps its prefix, a partially qualified one that relied on an enclosing namespace or a using outside the renamed one (`Old.Widget` inside `namespace App` for `App.Old`) is rewritten and then simplified as far as it still binds, and names relative to a renamed namespace or an alias of it stay. One semantic rewrite does all of this rather than Roslyn's `Renamer`, which can only change the last segment and also edits generated files. A nested declaration whose enclosing declaration stays changes only its own part (`namespace A { namespace B }` to `A.C` gives `namespace C`); when the enclosing part would have to change, the enclosing block is renamed too if it declares nothing else (`X.Y` gives `namespace X { namespace Y }`), and the rename is refused with `NamespaceBlockShared` (3130) if it does, or if blocks would have to merge. Also refused: a type that would land next to an existing type of the same name and arity, or a new namespace name that is already a type's (`NameCollision`), a namespace that also holds types of referenced assemblies (`NamespaceInMetadata`, 3131), an invalid or keyword name, the same name, and a namespace not declared in any source file. Generated files (under `obj`, `*.g.cs`, an `<auto-generated>` header) are never edited; one that still refers to the namespace, and a project-level `<Using Include>` or `<RootNamespace>` under the old name in a project file or a `Directory.Build.props`/`.targets` above it, are named in `warnings`, followed by the compiler errors the rename leaves in the changed files and, where a generated file or project-level using is involved, the whole project. `updateFolders` moves each file whose types all end up in one renamed namespace and which sits in the folder of its old namespace (the folder convention below the project's root namespace held) into the folder of its new one; a file elsewhere (e.g. `Old/Nested.cs` declaring `Old.Inner`) stays where it is with a warning, since moving it would change a layout the project chose. The moves follow the same rules as `move_type_to_namespace`'s `updateFileLocation` (SDK-style default globbing, MSBuild confirms each move once per project and a move it does not confirm is undone with `PARTIAL_SUCCESS`); a file that stays gets a warning saying why, and folders the moves leave empty are removed, and the warnings name moved files by their new paths. Files keep their encoding and line endings. `preview` lists each changed file with its first changed line before and after, and the planned moves. `IntroducedErrors` (also used by `change_signature`, `change_return_type` and `safe_delete`) now checks a file with `global using` directives on a fresh copy of the compilation, since Roslyn reports an unresolvable global using only to the first file it binds.
- **`inline_method`** (new tool; 46 tools in total): replaces calls to a method with its body, every call or the one at `callLine` (`callFile` defaults to `sourceFile`, `callColumn` picks one of several calls on the line; a reference there that is no call is named as such), and deletes the method when nothing references it any more (`deleteMethod`, default `true` when every call is inlined and `false` for one call; a method that implements an interface member is kept). A body that is an expression or a single `return` inlines into any expression position; a `void` method's statements replace a call that is a statement of its own, spliced into the enclosing statement list (a block, or the single statement, in an embedded position). Parameters are replaced by their arguments, parenthesized and cast to the parameter type where the call converted them (the simplifier removes what isn't needed); left-out optional arguments take their default (an enum default by its member), named arguments are matched by name, an expanded `params` array becomes `new T[] { ... }`, an extension call's receiver is the first parameter, and type parameters are replaced by the call's type arguments, inferred ones included. An instance call's receiver replaces `this` and the members the body reaches through it; types and static members the body names are written fully qualified and simplified to what the call site's usings allow, and the namespace of an extension method the body calls is imported where it is missing. Constants and reads of the caller's own locals are substituted as they are; other reads are substituted when the body runs no side effect before using them; a single argument with side effects is substituted when the body evaluates it exactly once, unconditionally and before any other side effect; everything else, the receiver included, and any parameter the body assigns, is first stored in a local in the original order, so every argument is evaluated as often and in the order it was. Those locals go before the call's statement, which must evaluate the call exactly once and evaluate nothing with side effects before it; locals and other names the body declares (pattern and `out` variables, lambda parameters included) are renamed when they would clash with a name at the call site. A call that can't be inlined this way is left as it is and listed in `warnings` with the reason: it needs locals in an expression-bodied member, an initializer, a lambda expression, a loop condition or a conditionally evaluated position; it is a conditional access (`?.`), inside an expression tree, or in a `checked`/`unchecked` context other than the method's; the body uses members not accessible there, `base` or an event outside the declaring type; a mutable struct receiver would have to be copied; or a member name of the inlined body would bind to another member there (checked after the edit, e.g. a member hidden in a derived class; a call through a type parameter's constraint that now binds to the type argument's implementation is accepted). Refused with `MethodNotInlinable` (3140): recursive, virtual, abstract, override, interface, explicit-implementation, partial, extern, async, iterator, unsafe and `[Conditional]` methods, `ref`/`out`/`in` parameters, a `ref` return, block bodies other than a single `return` (or a void body with an early `return`), throw-expression bodies, labels, `stackalloc`. `CallNotInlinable` (3141) when the picked call (or every call) is refused, `CallSiteNotFound` (2022) when there is no call. Method groups, `nameof` and crefs are left alone and keep the method. Compiler errors left in the touched files are added to `warnings`. Files keep their encoding and line endings; `preview` lists every call before and after and the deletion.
- **`pull_members_up`** (new tool; 47 tools in total): moves members of a type (`typeName`, `line` when the file has several of that name) into its direct base class, or declares them in an interface it implements (`targetType`, by simple or qualified name; a base class may be named too). `members` names fields, methods (every overload), properties, events (field-like or with accessors) and indexers (`this`); one variable of `int a, b;` moves alone. Into a base class, each declaration moves with its documentation comment and attributes (fields after the base's fields, other members at the end) and leaves the type, taking its comments and one blank line with it; a private member becomes protected (noted in `warnings`), a `private protected` one stays, or becomes protected when the base class is in another assembly, and `new` is dropped when there is nothing left to hide. With `makeAbstract`, methods, properties, indexers and events are declared `abstract` in the base class (signature, non-private accessors, doc comment; no body or attributes; `abstract override` for an override) and stay in the type as `override` without constraint clauses, while fields still move; a base class that isn't abstract is made abstract when nothing creates an instance of it (noted), and otherwise refused with `BaseClassInstantiated` (3152) listing the `new` expressions. Into an interface, a public instance method, property, indexer or event adds its signature (public accessors only, e.g. `{ get; }` for `{ get; private set; }`) and keeps its implementation as an implicit implementation; non-public members are refused (`MemberNotPublic`) rather than made public or explicit, which would change who can call them, and so are fields and static members. A type parameter of the type (`Cache<U> : Repository<U>`) is written as the target's (`List<U>` becomes `List<T>`); one the target has no counterpart for is refused with `TypeNotExpressible`. Refused with `MemberDependsOnDerived` (3150) when the moved code uses members of the type that stay behind (named in the message and in `details.dependencies`, to pull them up as well); `MemberConflict` (3151) when the target already declares the name or (for methods and indexers) the signature, or for an override of a member the base class declares itself; `MemberNotMoveable` for `base.` calls that would mean something else in the base class, constructors, operators, nested types, partial members, record parameters, `makeAbstract` on static members or properties with a private accessor, and types from a project the target's project doesn't reference. The usings the moved code needs (types, extension methods) are added to the target's file. Other classes derived from the base class that declare a member of the same name are noted (they now hide it, CS0108); compiler errors introduced in the files of the target, the type, the base class's other derived types or the interface's implementers (e.g. CS0534 or CS0535 for a member they now lack) are returned as `warnings`. Files keep their encoding and line endings (documentation comments carried into a file take its line ending); `preview` lists the members added to the target, the declarations removed and the members made overrides.
- `pull_members_up` takes `targetFile`, the absolute path of the file whose part of a partial target gets the members (and the usings they need). Without it the members go into the target's first part in a file that isn't generated, as before; a file without a part of the target, or a generated one, is refused with `InvalidTargetPath` (1002), naming the files the target is declared in. The CLI takes it as `--target-file`.
- `pull_members_up` adds static members to an interface as `static abstract` declarations: a public static method, property or event of the type (`public static string Kind => "square";`) is declared `static abstract string Kind { get; }` in the interface (`targetType`) and stays in the type as its implicit implementation. It needs C# 11 and a runtime with static virtual members in interfaces (.NET 7 or later) in the interface's project; otherwise the call is refused with `MemberNotMoveable` as before, now saying why. Other implementers that lack the member (CS0535) and the places that use the interface as a type argument, which an interface with static abstract members can no longer be (CS8920), are reported in `warnings`.
- `pull_members_up` pulls user-defined operators and conversions up into an interface. `members` names them as written, the word `operator` optional (`operator +` or `+` for every `+`, unary and binary; `operator checked +`, `operator ==`, `operator true`, `operator +=`; `explicit operator` for every explicit conversion, `explicit operator Money` for one), or by metadata name (`op_Addition`); a name that matches nothing lists the type's operators this way. In an interface with a self type parameter, the one the type passes itself as and that is constrained to the interface (`interface IAddable<TSelf> where TSelf : IAddable<TSelf>`, implemented as `Money : IAddable<Money>`), an operator is declared `static abstract` with the type written as that type parameter (`public static Money operator +(Money a, Money b)` becomes `static abstract TSelf operator +(TSelf a, TSelf b);`, also inside `TSelf[]` or `List<TSelf>`, and `static abstract explicit operator TSelf(int cents);`), and stays in the type as its implicit implementation; a C# 14 instance operator becomes `void operator +=(TSelf other);`. An interface without such a type parameter gets the operator as written when it already takes the interface (`static abstract IShape operator +(Square a, IShape b);`); otherwise, and for an unconstrained self type parameter (CS8924) or a `Money?` of a struct (which `TSelf?` doesn't mean), the call is refused with `MemberNotMoveable` saying why. The other one of `==`/`!=`, `<`/`>`, `<=`/`>=` and `true`/`false` (CS0216), the unchecked version of a checked operator (CS9025) and the checked version of an unchecked one are pulled up with it, each noted in `warnings`; so is code whose operator now binds to the interface's where it compiled before with another one (`a == b` on a class-constrained `T` compared references). Static abstract operators need C# 11 and .NET 7 like other static members; implementers lacking them (CS0535) and the interface as a type argument (CS8920) are reported; `==`/`!=` in an interface cause no CS0660/CS0661. Into a base class, static operators are refused with `MemberNotMoveable`: an operator must take the class that declares it (CS0563, a conversion convert from or to it, CS0556) and can't be abstract or virtual, so it would need another signature, and the message points to an interface with a self type parameter instead; C# 14 instance operators (`+=`, `++`), which can be abstract and virtual, move like methods (with `makeAbstract` declared abstract there and kept as overrides). `extract_base_class` still refuses operators.
- **`get_diagnostics` runs analyzers on request** — `includeAnalyzers: true` (CLI `--include-analyzers`) also runs each project's analyzer references through `CompilationWithAnalyzers`, so analyzer IDs such as `CA1822` or `IDE0005` can be listed and matched by `diagnosticIds`. For an SDK project these are the analyzers the build passes to the compiler: the .NET analyzers (CA rules, unless `EnableNETAnalyzers` is false), the code-style analyzers (IDE rules) only when the project sets `EnforceCodeStyleInBuild`, and those of package references. Severities come from `.editorconfig` and the global config files (`AnalysisLevel`) as in the build, `#pragma warning`, `[SuppressMessage]` and the projects' diagnostic suppressors apply (to compiler warnings too), and suppressed diagnostics are left out. On a probe with `AnalysisLevel` `latest-all`, `EnforceCodeStyleInBuild`, `GenerateDocumentationFile` and an `.editorconfig` raising IDE0005 / CA1822 to warnings, the list equals `dotnet build`'s warnings; without `GenerateDocumentationFile` the build reports `EnableGenerateDocumentationFile` where the tool reports the IDE0005 itself, because the workspace always parses documentation comments. `diagnosticIds` / `excludeDiagnosticIds` decide which analyzers run at all, `projectPath` which projects, and a `.cs` `sourceFile` runs them on that file only (analyzers that report at the end of the compilation, such as CA1812, still see the whole project). An analyzer that throws is reported as Roslyn's `AD0001` warning, a reference whose analyzers can't be listed, an analyzer reference MSBuild names but Roslyn can't resolve (e.g. a missing DLL; the load removes it, and only the Razor generator's used to be reported, as `RMCP0001`) or a project that can't be compiled as `RMCP0003`, and an analyzer reference that couldn't be loaded is the `RMCP0001` it always was. None of them fails the call; for the analyzers the call wanted (those of the projects it analyzes; with `diagnosticIds`, the analyzers that can report one of them) they mean the result is incomplete, so they are listed first, ahead of `maxResults`, and pass `diagnosticIds`, `excludeDiagnosticIds`, `messageFilter`, `severityFilter` and `sourceFile`; a `diagnosticIds: ["CA1822"]` call whose CA1822 analyzer throws returns the `AD0001` instead of an empty list. An `RMCP0001` about a project whose analyzers didn't run, or about an unresolved Razor generator reference, is filtered as before, and a call without `includeAnalyzers` reports no unresolved analyzer references, exactly as before. Off by default because it is slow: on this repository, warm, about 3.2-3.9 s for the whole solution (0.2 s without analyzers), 1.0-1.25 s for `RoslynMcp.Core` (0.07 s) and 0.65-0.85 s for one of its files.

### Changed
- **Tool result JSON is now human-readable** — results are tab-indented instead of minified, and non-ASCII / HTML-sensitive characters (umlauts, `<`, `>`, `&`) are emitted verbatim instead of `\uXXXX` escapes. All 41 tool handlers share one `ToolJsonOptions.Default` instance instead of each constructing identical serializer options; the CLI's JSON output uses the same encoder and tab indentation.
- Upgraded to **.NET 11** (`net11.0`, `global.json` pins SDK 11.0.100 with `latestFeature` roll-forward) and **xUnit v3** (4.x). Running the server now requires the .NET 11 runtime. Dependencies: Roslyn 5.12.0, Microsoft.Build.Framework 18.12.2 (plus `Microsoft.NET.StringTools` 18.12.2, which it now depends on, excluded from runtime output like Framework itself so MSBuildLocator's MSBL001 check passes), Microsoft.NET.Test.Sdk 18.12.0, xunit.runner.visualstudio 4.0.1, Microsoft.Testing.Extensions.CodeCoverage 18.12.0 (in place of coverlet.collector, see below).

- A project is now fully compiled at load time so the reported `workspaceLoadMs` reflects the real cold-load cost rather than deferring it to the first query.
- **`change_signature` changes the whole override / implementation family.** Changing one member of a family alone never compiles, so the change now also applies to what the method overrides (up to the base-most definition), its overrides (transitively, in every project of the solution), the interface members it implements implicitly or explicitly and their other implementations, and to the calls of all of them, `base.M(...)` included. Parameters correspond by position, since an override may name them differently: a rename in the request renames the parameter at that position in every member, with its uses in the bodies and documentation comments and the named arguments of the calls; without a rename each member keeps its own name. A type the request writes is resolved where the method is declared and written in each member's own context (`IEnumerable<T>` in `Repository<T>` becomes `IEnumerable<User>` in `UserRepository : Repository<User>`; `string?` is written `string` in a nullable-disabled file); a type that uses a type parameter with no counterpart in some member is refused (`TypeNotExpressible`, 3111). Explicit interface implementations get no default values (CS1066). When a member of the family is declared only in metadata (an override of `object.ToString`, an implementation of `IDisposable.Dispose`) or in generated code, the tool refuses and names it (`FamilyMemberNotInSource`, 3110), since that member cannot change. There is no option to change one member alone. (`parameters` is now a list of changes, see below.) `line` may be any line from the declaration's first attribute or modifier to its name. Like `change_return_type`, the result lists under `warnings` the compiler errors the change leaves in the affected documents (the declaring files, the files declaring the members' types, and every file that references a member), such as a method group converted to a delegate it no longer matches or a removed parameter the body still uses, and each `default /* TODO */` placeholder passed for a parameter without a default value (`path(line,column): TODO: ...`).
- **Unknown argument keys are refused** (server and CLI). Every tool's schema says `additionalProperties: false`, but the tools deserialized their arguments leniently, so a mistyped key or one in another case (`MaxResults`, `filePath`) was dropped and the option silently took its default. The server now checks each `tools/call`'s arguments against the tool's input schema before the tool runs, including the entries of `change_signature`'s `parameters` (whose schema now says `additionalProperties: false` too), and refuses unknown keys with a tool error like a missing argument: code `1018` (`UnknownParameter`), a message naming each key with the key it probably means (`'MaxResults' (did you mean 'maxResults'?)`, also for small typos) and the keys the tool takes, and `details.unknownArguments` / `details.validArguments`. Argument names are case-sensitive. Arguments that are not a JSON object are refused with `1017`. The CLI refuses an option the tool does not take, or an unknown key inside a JSON value (`--parameters '[{"orignalName": ...}]'`), with exit code 2, the closest valid option and the list of valid options; options stay case-insensitive there (`--Source-File` works, as the CLI reads parameters case-insensitively). A test checks that every tool's schema declares exactly the keys its handler reads, with matching types. **This changes behaviour for clients that sent extra keys**: such calls used to run and now fail.
- **`change_signature`'s `parameters` is a list of changes.** It was read as the new parameter list itself, so a parameter the request did not list was dropped (`remove: true` was the same as leaving it out), the list order was the new order, and a parameter listed without `defaultValue` lost its default. Now a parameter that is not listed stays, in its relative order. An entry with `originalName` changes that parameter: `name` renames it, `type` retypes it, `defaultValue` sets its default (left out, the default stays; `""` removes it), `newPosition` moves it (0-based index in the new list; the parameters that do not move keep their order in the remaining places), and `remove: true` removes it (its other fields must then be left out or equal the parameter's, so older requests that repeat `name` still work). An entry without `originalName` adds a parameter (`name` and `type` required; `name` is no longer required otherwise) at `newPosition` or at the end. **A new parameter with a default value is no longer written into existing calls** (`Sum(1, 2)` stayed `Sum(1, 2)` instead of becoming `Sum(1, 2, 0)`); an argument after it that was positional is passed by name instead (`Mix(1, 5)` → `Mix(1, b: 5)`), and only when that is impossible (several expanded `params` arguments) does the call pass the default. A new parameter without a default still gets the `default /* TODO */` placeholder and a warning; calls that are left as they are no longer count in `referencesUpdated`. Refused before anything changes: an unknown `originalName` (`2016`), a parameter listed twice (`1017`), two parameters that would end up with one name (`3010`), a `newPosition` outside the new list or asked for twice (`1011`), and, as before, a required parameter after optional ones (`1011`). A rename is also refused (`3010`) when, in any member of the override / implementation family (all of them are renamed together), the new name is already declared in the body (a local, a lambda or local function parameter, a query range variable, a pattern variable, a local function) or used there by simple name for something else (a field, property, method or type: `total += amount` renamed to `total` would read the parameter), is the method's type parameter, or is the name of another of that member's parameters; `this.total` does not count, and swapping two names works.
- **Argument values are checked against the schema too.** A value of the wrong type reached the tool, whose deserializer failed with its own message as an `INTERNAL_ERROR` (`"line": "ten"` gave "The JSON value could not be converted to System.Nullable`1[System.Int32]. Path: $.line ..."). The server now refuses, before the tool runs, a value that is not of the schema's type (an integer must be a whole number in the 32-bit range unless the schema says `"format": "int64"`), not one of its `enum` values (compared ignoring case, as the tools read them; `add_null_checks` used to take any `style` other than `throw` as `guard`), or below its `minimum` / above its `maximum`, at every level including `change_signature`'s `parameters` entries (a `null` entry is refused). The error is `1017` (`InvalidParameterValue`) naming each key, the expected type and the value given (`line must be an integer, not the string "ten".`), with `details.invalidArguments`. An argument that is `null` now counts as left out: it is removed before the tool runs, so `"startLine": null` is reported as missing instead of failing to deserialize. The CLI checks the values inside JSON options the same way and also leaves their `null` properties out. The test that keeps schemas and handlers in sync also checks the integer width and that `enum` is only declared on strings.
- `change_signature` with `defaultValue: ""` (removing a parameter's default value) no longer gives the calls that left the argument out a `default /* TODO */` placeholder and a warning: they pass the value they used to get, so the code behaves the same (`m.Mix(1, 2)` with `int c = 7` becomes `m.Mix(1, 2, 7)`, `m.Mix(b: 1, a: 2)` becomes `m.Mix(b: 1, a: 2, c: 7)`). The value is the default of the member the call binds to (a call through the interface gets the interface's default, a call on the class the class's), written as its declaration writes it, with the constants, enum members and types it names qualified so they mean the same at the call (`Limits.Max`, `Mode.Safe`, shortened as far as the call's usings allow); where it names something the call cannot access (a private constant) or cannot be written there, its value is written as a literal. When the request also changes the parameter's type, the old value need not fit, so the placeholder stays.

### Removed
- `rename_symbol` no longer advertises `renameImplementations`. It was never read: Roslyn's renamer always renames interface implementations and overrides together with the member, so `false` had no effect. The parameter is gone from the tool schema, the contract and the CLI (`--rename-implementations`), and the tool description now says that implementations and overrides are always renamed.

### Fixed
- `pull_members_up` into an interface with a self type parameter (`interface IAddable<TSelf> where TSelf : IAddable<TSelf>`, implemented as `Money : IAddable<Money>`) writes the type as that parameter in the signature of every member it adds, not only of operators: `public Money Add(Money other)` becomes `TSelf Add(TSelf other);`, `public static Money Zero` becomes `static abstract TSelf Zero { get; }`, likewise in type arguments, arrays, indexers, events and constraints (`where T : TSelf`). The interface named the one implementer instead (`Money Add(Money other);`), which every other implementer had to implement as such and which an interface in a project that can't see `Money` couldn't compile. The type keeps its signatures and implements the members implicitly; a `Money? other = null` parameter is written `TSelf? other = default` (a type parameter has no conversion from null, CS1750), and a struct's `Money?` (`Nullable<Money>`, which `TSelf?` doesn't mean) is refused with `MemberNotMoveable` for every member, as it was for operators.
- `pull_members_up` writes reference types without their `?` where the target's part has nullable annotations disabled. Moved members (`string? Name`, `List<string?>`, an unconstrained `T?`, also locals in moved bodies) and interface or abstract signatures kept the `?`, which warned CS8632 there; a value type's `?` (`int?`) stays, like `inline_method` does it.
- `move_type_to_namespace` and `rename_namespace` rewrite component tags written with the namespace. The Razor compiler binds `<Probe.Panel />` / `</Probe.Panel>` by that name, so after moving `Panel` to `Probe.Parts` (or renaming `Probe` to another namespace) the tag no longer bound and silently became an HTML element (only an RZ10012 build warning); `rename_namespace` listed such lines as mentions, `move_type_to_namespace` did not see them at all (and added a `@using` that doesn't help a qualified tag). Now `RazorComponentTags` rewrites start and end tags whose name is the component's old full name (`move_type_to_namespace`, for a type implementing `IComponent`, in the Razor files of its project and the projects depending on it) or starts with the old namespace (`rename_namespace`), matching whole dotted segments right after `<` or `</`, outside `@code` / `@functions` blocks and string literals; a file that only uses qualified tags no longer gets a `@using`.
- `move_type_to_namespace` keeps Razor files working and reports what the move breaks. It updated the using directives of C# files only: a Razor component that used the type (`@Gauge.Read()`, or a C# component as a tag, `<Panel />`) kept looking for it in the old namespace, so the generated code no longer compiled or, for a component tag, silently became a plain HTML element (RZ10012 warning). Now a Razor file whose code names the type by its simple name, or as the Razor compiler binds a component, gets `@using New.Namespace` after its leading `@using` lines (or after `@page` / `@namespace`, else at the top), unless the file or an `_Imports.razor` / `_ViewImports.cshtml` above it already imports it; a name the Razor file writes with the old namespace (`@Probe.Gauge.Read()`) is listed in `warnings` ("uses 'Probe.Gauge', now 'Probe.Meters.Gauge'; qualify it here by hand"), as is a reference in other generated code; a generated `*.g.cs` file is no longer edited; and the compiler errors the move leaves anywhere are reported in `warnings` (`IntroducedErrors.FindInProjectsAsync`, matched without line numbers since the added directives move lines, also in generated code).
- `pull_members_up`, `safe_delete`, `rename_namespace`, `encapsulate_field`, `convert_property`, `extract_base_class`, `extract_interface` (when it adds the interface to the type) and `inline_method` (when it deletes the method) report compiler errors the way `change_signature` does: in every file of the projects the change touches and of the projects that depend on them, generated code included. They checked only the files they edited or that referenced what changed, so a use the change broke elsewhere, such as a Razor component reading a field that `encapsulate_field` made private (`Widget.razor(5,9): error CS0122`) or one `convert_property` removed, was not in `warnings`; `extract_interface` reported no errors at all. Purely local tools (`extract_method` and `inline_method` when it keeps the method) still check only the files they edit. On RoslynMcp.sln a `rename_namespace` preview of `RoslynMcp.Core.Refactoring.Signature` takes about 1.4 s warm (2.5–2.8 s with the old per-file check, which read many whole projects file by file).
- Refactorings leave references in generated code alone and say where to change them. `change_signature` failed with "Unexpected error: Object reference not set to an instance of an object" when a call to the method was in a source generator's output, such as a Razor component's C# (`<p>@Api.Format(2, "b")</p>`), because it tried to edit that generated document. Now a call there that would change is skipped and listed in `warnings` at the place its `#line` directive maps it to (`Widget.razor(3,9): the call to 'Api.Format(int, string)' is in code generated from this file and was not rewritten; change it here by hand.`). The same rule, through one helper (`GeneratedReferences`), applies to the references `rename_symbol` (Roslyn's renamer leaves generated code alone), `convert_to_async`, `introduce_parameter`, `encapsulate_field`, `convert_property` and `inline_method` do not edit there; `inline_method` keeps the method for such a call; `safe_delete` lists a reference in generated code at its `.razor` line (kind `generated`). On-disk generated files (`*.g.cs`, `obj/`) are treated the same way.
- Symbols that can come from different compilations are compared as the same declaration (documentation ID plus assembly name) through one helper, `SymbolIdentity`, instead of `SymbolEqualityComparer`, which tells the instances of one declaration apart when another project or another target framework's compilation sees it. `pull_members_up` took the moved type itself, as the other target framework of a multi-targeted project compiles it, for another derived type and warned that its member now hides the pulled-up one (CS0108); `find_implementations` could list an implementation once per project that sees it; `implement_interface` could add an interface found through another project again; `inline_method`'s check that an inlined name still binds to its member ignored the assembly; and `inline_method`'s same-type check, `encapsulate_field`'s and `convert_property`'s inside-the-type checks, the usings moved code gets in another project's file (an extension method's class already in scope there), `move_type_to_namespace`'s collision check and generated overrides' same-assembly check compared one compilation's symbols with another's. `MemberFamily`, `safe_delete`, `find_implementations`, `find_unused_symbols` and `pull_members_up`'s own versions of this comparison now use the helper too.
- `change_signature` rewrites two kinds of calls it used to leave alone (their errors only showed up in `warnings`). An extension method called on a receiver whose `this` parameter moves or is removed becomes a plain static method (the `this` modifier goes, `warnings` says so) and its calls take the static form with the receiver as the first argument: `s.Pad(5, '*')` becomes `Text.Pad(5, '*', s)`, or `Text.Tag("t")` when the receiver's parameter is removed (a conditional call `s?.Pad(...)` is still left alone and reported). Expanded `params` arguments that would need a name are passed as one collection, by name: `Join(separator: ",", trim: true, parts: ["a", "b"])`, or `parts: new string[] { "a", "b" }` before C# 12. A named argument of a removed parameter goes with it (already so; now tested).
- `change_signature` and `change_return_type` change every target framework of a multi-targeted project. They edited a file through one framework's document, so a call, a use of a renamed parameter or an override in an `#if` branch only another framework compiles kept the old signature (and the commit wrote whichever framework's version came last, possibly dropping the edits); a method declared only in such a branch was not found at all. Now each member is followed in every framework (also to an override only one of them compiles), each framework's document gets the edits of its own branches, and `LinkedDocuments.MergeAsync` (which replaces the rename-only line merge, also for `rename_symbol`, `rename_namespace` and `convert_to_async`) combines them line by line, lines added or removed included; a line two frameworks change differently keeps the declaring document's version and is listed in `warnings`. A call and a declaration that several frameworks compile are counted once. A new argument in a call that puts each argument on its own line gets that line's indentation instead of starting at column 0.
- `change_signature` and `change_return_type` write a type that mentions a type parameter into every member of the family also when it sits in a pointer, a function pointer or a generic containing type. Starting from `IParse<TSelf>.Parse`, `TSelf*`, `delegate*<TSelf, void>` (calling convention and `ref` / `in` / `out` kept) or `Outer<TSelf>.Inner` was refused with 3111 although `Num : IParse<Num>` can say `Num*`, `delegate*<Num, void>` and `Outer<Num>.Inner`; the type is now translated symbol by symbol (arrays, tuples and nullable types included) and refused only when it uses a type parameter the member has no counterpart for.
- `change_signature`, `change_return_type`, `convert_to_async` and `introduce_parameter` report the compiler errors a change causes anywhere in the projects it touches and in the projects that depend on them. Only the files declaring the changed members (or their types) and the files referencing them were checked, so a file that never names the method but calls another overload that the change made ambiguous (`Format.Show(1, 2)` after `Show(long, string)` became `Show(long, int)`, CS0121), or code in generated files, compiled with errors that `warnings` didn't list. Each project's new compilation is now checked as a whole and only the files with errors are compared with before (about 1.2 s for a change in `RoslynMcp.Core` with its five dependent projects, warm); errors without a location (a program left without an entry point) are listed as `project: error id: message`.
- `move_type_to_file` indents the moved type where it lands, and `extract_interface` lays out its new file like `extract_base_class`. A type moved into an existing file's block namespace kept the indentation it had in its own file (column 0 from a file-scoped namespace), so it sat at the left margin inside `namespace App { ... }`; it now takes the indentation of the block's members (one level in an empty block) after a blank line, its documentation comment and attributes included, and a type from a block namespace moved into a new file starts at column 0. Only the indentation at the start of each line changes: the lines inside a string literal (or a block comment) stay as they are, and directives stay at column 0. The file `extract_interface` creates had no blank line after `namespace X;` and no line break at its end; it now has a blank line after the usings and after the namespace line and ends in a line break.
- A file created for moved code gets only the usings that code needs, and `move_type_to_file` into an existing file adds the usings the type needs. `extract_base_class`, `extract_interface` (with `targetFile`) and `move_type_to_file` copied every using of the source file into the new file, needed or not (also `global using`s, which apply to it anyway); now the source's plain, static and alias usings are copied in their order and those the compiler reports unnecessary in the new file (CS8019) are dropped, as every target framework of the project compiles it, so a using that only code in another framework's `#if` branch needs stays. `move_type_to_file` into an existing file added no usings at all, so the moved type could fail to compile there (CS0246); it now adds the namespaces, `using static` and aliases the type needs that the file lacks, the way `pull_members_up` does (a name that means something else in the file is written qualified), sorted into their group where the file has its usings (also inside a namespace block, indented like the others). The files whose text a move changes are given to every target framework's document before the usings it left unused are removed. A new file of `move_type_to_file` has one blank line after `namespace X;` instead of two (the blank line before the type in the source came along).
- `pull_members_up`, `extract_base_class` (with `targetFile`) and `move_type_to_file` remove the `using` directives that only the moved code used from the file it leaves. They stayed behind unused (`Square.cs` kept `using static System.Math;` after its only user moved into the base class); now a directive the compiler reports unnecessary (CS8019) after the move but not before goes, in every target framework's view of a multi-targeted file, like `safe_delete` does it. Usings that were unused already, those the remaining code uses, and global usings stay. `preview` lists each removal ("Remove 'using System.Text;', which only the moved code used", with its line) and `usingDirectivesRemoved` counts them. `move_type_to_file`'s preview also names the target file for its "Create file" / "Add declaration" change instead of the source file.
- `pull_members_up` with `makeAbstract` no longer makes a base class abstract that is created without a `new` expression. Only `new Base()` counted, so a base passed as the type argument of a `new()`-constrained type parameter (`Factory.Make<Base>()`, `new Pool<Base>()`, or inferred as in `Factory.Clone(item)` for a `Base item`) or created with `Activator.CreateInstance<Base>()` or `Activator.CreateInstance(typeof(Base))` was made abstract, and the code then failed to compile (CS0310) or threw at run time. These now refuse the call with `BaseClassInstantiated` (3152) like a `new` expression, each location named with how it creates the class. Inferred type arguments are found in the files that name the class; creation through reflection by name (`Type.GetType("App.Base")`) is not seen. The count of further locations in the message counts each location once.
- `pull_members_up` carries the `using static` and alias directives the moved code needs into the target's file. Only namespaces of types and extension methods were added, so a member using `Max(a, b)` through `using static System.Math;`, a constant or nested type through `using static App.Units;` (or an enclosing type), or `new Sb()` through `using Sb = System.Text.StringBuilder;` left errors in `warnings`. Now the target's file gets a `using static` of the type of each static member or nested type the moved code names without its type and that doesn't bind there already, and each alias it uses that the file doesn't have, in the groups plain, static, alias, each sorted. A name that would mean something else in the target (an alias of that name for another type, a type of that name in the target's namespace, or a member of the target with that name) is written qualified instead (`new System.Text.StringBuilder()`, `new App.Tools.Helper()`, `Math.Max(a, b)`); before, importing the namespace of such a type left the name bound to the other one. An attribute written without its `Attribute` suffix (`[Obsolete]`) also gets its namespace imported now.
- `inline_method` keeps what a call evaluated and when it threw. A receiver the body doesn't use was dropped without a trace when it had no side effects, and one with side effects became an unused local (`Calc calc = GetCalc();`); now an unused receiver or argument with side effects (or that may throw) is evaluated as a statement of its own (`GetCalc();`, `_ = box.Value;`), one without is dropped, and a receiver that may be null (not `this`, a value type, a `new` expression, or non-null by the nullable analysis where nullable warnings are enabled) is reported in `warnings` when the body doesn't dereference it before anything else, since a null one no longer throws `NullReferenceException` where the call did (`inlined, but a null 'box' no longer throws NullReferenceException: the inlined code doesn't use it`). An argument with side effects is substituted at its only use only when nothing before that use may throw: division and remainder, `decimal` arithmetic, arithmetic and conversions in a `checked` context or a project built with `<CheckForOverflowUnderflow>`, unboxing and reference casts, element access, a member access on something that may be null, and a member access of `this` when the receiver may be null; `Grow(big, Next())` with `big + big + step` evaluated `Next()` after the overflow, and `none.Plus(Next())` with `Step + a` threw before `Next()` ran. A field or auto-property read on something that may be null counts as possibly throwing too. Reads of auto-properties declared in source (not virtual, abstract or in an interface) no longer count as side effects, so `item.Count + item.Id + Next()` needs no local, and a `readonly` field or get-only auto-property read outside a constructor is substituted like a local (`Second(item.Id, Next())` becomes `Next() - item.Id`). An argument with a `!` (`null!`) is no longer refused as "a params collection in expanded form".
- `inline_method` imports the namespaces of the extension methods the body uses without naming them: the methods of a LINQ query (`from v in values where v > 0 select v`), a collection initializer's `Add`, a foreach's `GetEnumerator`, the `Deconstruct` of a deconstruction (`var (a, b) = x;`, also in a foreach) or of a positional pattern (`x is (0, _)`), and an await's `GetAwaiter`. Only extension methods called by name had their namespace imported, so a body inlined into a file without, say, `using System.Linq;` left CS1935 there (listed in `warnings`).
- `inline_method` no longer writes nullable annotations into code where they are disabled. The body's `string?`, `List<string?>`, `(string?)null` or an unconstrained `T?` were copied as written into a call site under `#nullable disable` (or in a project without `<Nullable>`), which warned CS8632; there a nullable reference type, or a type parameter that isn't a value type, is now written without its `?`, while `int?` and `T?` of a value type stay.
- `inline_method` inlines a void method whose body declares a generic local function. A call of such a function binds to the constructed function (`Describe<int>`), which wasn't recognized as the body's own, so the copy called it as a member of the method's class (`Program.Describe(1)`, or `this.Describe(1)`) and the call was refused ("'Add' in the body would refer to something else there"). Now the local function is copied with the rest of the body and renamed where the call site already uses its name, its type parameters (`Describe1<T1>`) and parameters included.
- `rename_namespace` also rewrites the Razor directives that take a type: in `@inherits`, `@inject`, `@model`, `@implements`, `@attribute`, `@typeparam … where …` and `@layout`, the old namespace where it starts a qualified name (`@inherits Company.Old.BasePage`, `IEnumerable<Company.Old.Model>`, also after `global::`) becomes the new one, matched segment by segment and outside string literals; they were only reported. What is left (C# in `@code`, markup, string literals, names relative to a `@using`) is still listed in `warnings`.
- `rename_namespace` keeps extension method calls inside a renamed declaration calling their method. A call like `3.Twice()` inside `namespace Company.Old` that found `Company.Ext.Twice` through the enclosing namespace no longer compiled after renaming to `Other.New` (CS1061), or silently called an `Other.Hijack.Twice` the new surroundings bring in; it was only reported. Now a `using Company;` is added where the file keeps its usings (inside the renamed declaration when it has usings or shares the file with other declarations, else at the top of the file), or inside the declaration when that is not enough to win over the new surroundings. It is kept only when every such call calls its old method again in every target framework and the file gets no new compiler error; otherwise the file is left as it is and a call that now calls another method is reported in `warnings`. `usingDirectivesAdded` counts the added usings.
- `find_unused_symbols` reports fields and auto-properties that are assigned but never read (what IDE0052 calls "assigned but its value is never read"). It counted every write as a use, so a field that was only assigned never showed up. Such a symbol is now listed with `reason: "write-only"` (every entry has a `reason`; the others say `"unreferenced"`), since deleting it means deleting the assignments too: `safe_delete` refuses it while they exist, as writes are references. Using directives that applied to the type go with it, written fully qualified where they relied on the old enclosing namespace (`using Models;` for `App.Models`), also when a namespace declaration is only renamed.

The server learns of such an edit from its file watcher, 50-200 ms later, and the commit never compared the disk with the text the refactoring started from, so a refactoring computed in between wrote the older text back: renaming while a script rewrote the file like an IDE save lost the script's edit in 5 of 12 tries. Every commit now reads each file it writes, deletes or creates once (the read that already chose its encoding) and compares it, decoded as the watcher decodes it, with the refactoring's snapshot. When another program changed, deleted or created one, nothing is written: the files are taken over (text read again; a created or deleted file re-evaluates its project), the refactoring is computed once more on them, and its `warnings` say so (`'…' changed on disk while the refactoring ran (another program wrote it); it was computed again on the new text.`); in the same test no edit was lost and 5 of 12 renames were computed again. If the files change again during that second attempt, it fails with `WorkspaceBusy` (4001) and writes nothing. A file deleted on disk is no longer written back, and a file that exists where a refactoring would create one but is not in the workspace is no longer overwritten (when the project's re-evaluation finds it, `move_type_to_file` moves the type into it). A preview computed on stale text warns that the workspace is behind the disk. A type rename's old file is now deleted by the commit, right after the renamed file is written.

Each process has writer sections of its own, so even with the disk check one process could write a file between another one's check and its write, and two atomic writes of one file at once failed with `FilesystemError` (4002) ("Cannot create a file when that file already exists"). Live, two servers renaming different methods of one file, eight each, all at once, lost 4, 7 and 6 of the 16 renames per run before (1 or 2 more failed with 4002), and 1 or 2 with the disk check alone. A new spelling of an existing file's name (a type renamed `Foo` to `foo` with `renameFile`) still deletes the file first, as a replace keeps the old spelling. The refusal (`InvalidParameterPosition`, 1011) names both parameters and happens before anything is changed; giving the later parameter a `defaultValue`, or moving it before the optional ones, makes the list valid, and a trailing `params` array may still follow optional parameters.
- Generated stubs and signatures compile without implicit usings and with names that are keywords. `implement_interface` and `generate_overrides` threw a bare `NotImplementedException`, and `generate_constructor` and `add_null_checks` used a bare `ArgumentNullException`, both of which need `using System;`; they are now written `System.NotImplementedException` / `System.ArgumentNullException` where no using allows the short name. A parameter, member or type parameter whose name is a keyword (`int @event`) lost its `@` in the stubs of `implement_interface` and `generate_overrides`, the members of `extract_interface`, the constructor of `generate_constructor` (also for a field `_class`, whose parameter is `@class`), the checks of `add_null_checks`, the members `generate_tostring` and `generate_equals_hashcode` read, and the parameters `extract_method` and `introduce_parameter` declare; it is now written verbatim. `introduce_parameter` also no longer copies the local's indentation into the parameter list.
- `generate_equals_hashcode` writes code that compiles without implicit usings. `EqualityComparer<T>` and `HashCode` were bare names that need `using System.Collections.Generic;` and `using System;`; they are now written fully qualified and shortened as far as the file's usings allow, like the other generated type names. The `Equals` parameter is `object?` only where nullable annotations are enabled (it caused CS8632 elsewhere), a generic type is matched as `obj is Box<T> other` (`Box other` did not compile), and fields of struct or type-parameter types are compared with `EqualityComparer<T>` instead of `==` (CS0019). With more than one comparison, `Equals` puts each operand of its `&&` chain on a line of its own, aligned under the first one as Visual Studio's generator does, instead of one line that could run past 250 characters.
- `extract_variable` with `useVar: false` writes `?` only where nullable annotations are enabled. A variable for a call declared in annotated code (`string? Find()`) was declared as `string?` in a nullable-disabled file as well, which is warning CS8632; it is now written like the types other tools generate (`string` there, `List<string>` for `List<string?>`). `extract_constant` writes its type the same way.
- `extract_variable` and `extract_constant` extract `-2147483648` and `-9223372036854775808L` as a whole when the selection is the number after the minus. That number alone is a `uint` (`ulong`) that only the minus turns into `int.MinValue` (`long.MinValue`), so the extracted operand made `-x` a `long` or did not compile (CS0266, CS0023). `extract_constant` also accepts a selected signed number such as `-5`, which it reported as "no literal", and `replaceAll` then replaces the other `-5`s.
- `extract_constant` with `replaceAll` replaces only the literals with the extracted constant's type and value. It compared the literals' value text, so extracting `1` also replaced `1L`, `1u`, `1f` and `1.0` with an `int` constant, which changed the overload a call picked or the result of a division, or no longer compiled. Now `1.0` and `1.00` (or `"a"` and `@"a"`) match, while `1` and `1L` do not.
- `rename_symbol` renames the references in every `#if` branch of a multi-targeted project. Roslyn's renamer renames the copy of a file that each target framework compiles on its own, and only one copy was written, so renaming `Read` to `Fetch` left `Read()` in the `#else` branch the other framework compiles, whose build then broke. The copies' renames are now merged line by line (the merge `convert_to_async` already did, now shared), a renamed type's file moves for every target framework (the other framework's copy kept pointing at the deleted file), and a file is listed once in `filesModified`.
- New names are checked by one rule in every tool that declares one: `rename_symbol`, `extract_method`, `extract_variable`, `extract_constant`, `encapsulate_field` (`propertyName`), `extract_interface`, `extract_base_class`, `change_signature` (parameter names) and the namespaces of `rename_namespace` and `move_type_to_namespace`. Any C# identifier is accepted, non-ASCII ones such as `Größe` or `Λ` included, which `rename_symbol` and the namespace tools refused; a reserved keyword is refused with `ReservedKeyword` (3011) unless it is written verbatim (`@class`), where `extract_variable` and `extract_constant` used to accept `class` or `int` and `change_signature` wrote `int event`, none of which compiled. Contextual keywords such as `var`, `async` or `value` are accepted where they compile; a type cannot be named `record`, `required`, `scoped`, `file` or `extension` unless verbatim (`rename_symbol` refuses them even verbatim, since Roslyn's renamer writes them without `@`), `await` cannot name a local or method inside an async function, and namespace segments must be plain identifiers.
- `convert_to_async` produces code that compiles. With `renameToAsync` (the default) callers kept the old name, no `await` was ever inserted, and `Task<T>` got `?` even in nullable-disabled code. The method is now renamed first with Roslyn's renamer, so every reference follows, then made `async`: waits on a task (`.Result`, `.Wait()`, `.GetAwaiter().GetResult()`) and discarded tasks in its body are awaited, async callers await the call, and the callers it cannot await are listed in `warnings` with the compiler errors this causes. New refusals: `NotConvertibleToAsync` (3083: no body, `ref`/`out`/`in` parameters, `ref` return, already returns a task) and `AsyncMemberInFamily` (3084: virtual, abstract, override or interface implementation).
- Files that are not UTF-8 (windows-1252 with umlauts, as legacy code often is) are no longer garbled. The file watcher's sync, the project re-evaluation that picks up new files and the loader for standalone `.cs` files read every file without byte order mark as UTF-8, so an edit made outside the server turned each umlaut into U+FFFD, and the next refactoring of that file wrote the replacement characters to disk for good; and every refactoring rewrote such a file as UTF-8, even one MSBuild had read correctly. Files are now decoded as the compiler decodes them (byte order mark, else the project's `CodePage`, else UTF-8 when the bytes are valid UTF-8, else the system's ANSI code page), and each file is written back in the encoding its text was decoded with, so the bytes of the text a refactoring leaves alone stay as they were. A character the file's code page cannot represent is no longer written as `?` or a look-alike (windows-1252 writes `ā` as `a`): the file is saved as UTF-8 with BOM instead, and the result's `warnings` say so. A file whose bytes are not valid in its own encoding (a UTF-8 byte order mark in front of windows-1252 text) is not rewritten; the refactoring fails with `FilesystemError` (4002) before writing anything. A file converted outside the server (from windows-1252 to UTF-8 without BOM, say) is written in its new encoding from then on.
- Refactorings that run at the same time no longer undo each other. The server handles every request on its own task, so two refactorings of one workspace could start from the same snapshot, and a commit writes everything that differs from the current solution: whichever committed last put the other's files back as they were. Eight concurrent `rename_symbol` calls on one file kept a single rename, and a type rename that renames its file, run next to another rename, left both the old and the new file behind (CS0101). Refactorings of a workspace, previews included, now run one after another, each on the solution the one before committed; queries still run in parallel. A commit that is not built on the current solution is refused with `WorkspaceBusy` (4001) and writes nothing.
- A cached workspace is no longer leaked when two threads tear it down at once, e.g. the idle sweep evicting it just as a project-file change invalidates it. Both walked the entry's list of file watchers while one of them cleared it; the exception that followed skipped disposing the workspace (its MSBuild build host and the shadow-copied analyzers stayed loaded), and the entry was never torn down again. The watchers are now handed to exactly one of the teardowns.
- A workspace that has already been replaced in the cache no longer evicts its replacement. A file-watcher callback still running for the old entry (a project re-evaluation that failed because the entry was torn down under it, or an event that arrived just as the entry was invalidated) invalidated whichever entry the cache held for the solution by then, so the freshly loaded workspace was discarded and loaded a second time. A callback now invalidates only its own entry.
- A file that a refactoring creates or moves no longer drops out of the cached workspace when a project re-evaluation was already under way. After a `.cs` file appears or disappears, the watcher re-evaluates the project with MSBuild first and edits the solution later, once no tool call is running; a file that a call created (`move_type_to_file`, `extract_interface`) or moved (`move_type_to_namespace` with `updateFileLocation`, `rename_namespace` with `updateFolders`) in between was missing from that evaluation and was removed, so later calls neither saw nor updated it until the workspace was reloaded. The re-evaluation now removes a document only once its file is gone from disk.
- A refactoring no longer undoes an edit that the call just before it made. The file watcher read a changed file as soon as it saw the change but applied the text only once no tool call was running; when the next call edited the same file in between, the watcher then put the older text back into the cached workspace, and the call after that wrote it to disk. Ten `inline_method` calls in quick succession showed it: `inline Add` wrote back the `"hi".Shout()` that `inline Shout` had just inlined. The watcher now reads the file only while it has the workspace to itself, when the disk holds every committed edit, and leaves a document alone when its text is already current (the reread after an atomic save included).
- `inline_method` inlines into top-level statements like into a method body: the locals an argument needs and a void method's statements become top-level statements of their own, in place, instead of a new `{ ... }` block (which also hid a declaration such as `var y = Util.Sq(Next());` from the statements after it, so that call used to be refused). A block written on one line (`{ return Sq(Next()); }`) that gains statements is laid out with its braces on lines of their own instead of keeping `}` on the last statement's line. Generated statements end in a plain line break, so no blank line appears between them and the statement after them.
- Removing several adjacent members (`pull_members_up`, and `extract_base_class` below) no longer leaves a blank line after the type's `{` or before its `}`. Each declaration's span decided on its own about the blank line next to it, as if its neighbours stayed; declarations separated only by blank lines are now removed as one block (`DeclarationRemoval.Spans`), whose surrounding blank lines are judged once.
- `extract_base_class` returns the compiler errors the extraction introduces as `warnings`, like `pull_members_up` (e.g. CS0191 when an extracted `readonly` field is still assigned in the type's constructor), checking the type's file, the new base class's file and the files referencing the extracted members. Extracted members leave the type's text with their comments, as in `safe_delete`, instead of being dropped from the syntax tree, which left a blank line after `{`; the generated base class separates its members by a blank line.
- `extract_base_class` picks members like `pull_members_up` and shares its selection, accessibility and dependency checks. Field-like events, indexers (`this`) and the second and later variables of `int a, b;` were reported as "Members not found" (only the named variable moves now, the others stay); a `private protected` member came out as `protected protected` (it stays `private protected`; a private member, also one without an accessibility modifier, becomes `protected`); and a member that used private members staying in the type was moved anyway, leaving code that didn't compile. Such a move is now refused with `MemberDependsOnDerived` (3150), naming the members to extract as well.
- `change_signature` keeps each call's argument order, so the arguments are evaluated as before. Calls were rewritten into the new declaration order: adding a parameter turned `M(b: Next(), a: Next())` into `M(a: Next(), b: Next(), 0)`, which evaluates the two `Next()` the other way round. Now an argument of a removed parameter is dropped in place and a named argument is renamed in place; only positional arguments move when parameters are reordered; a new argument after a named one is passed by name (`M(b: 2, a: 1, c: 0)`); and from the first argument that would be out of position on, the arguments are named instead of moved (CS8323). An optional parameter a call leaves out stays left out; its default value used to be written into the call.
- `change_signature` no longer breaks the code it edits. A kept parameter was rebuilt from its type's display string, so `ref`/`out`/`in`/`params`/`this` and attributes were dropped and the type came out fully qualified (`System.Collections.Generic.List<int>`); it now keeps its own declaration apart from what the request changes. A renamed parameter kept its old name in the method body. Call sites were located by their original positions in documents that had already been edited, so a call after the changed declaration, or a second call in the same file, could hit the wrong node; all edits are now computed against the original syntax and applied in one pass. A method passed as a method group (`Run(Process)`) had the arguments of the enclosing call rewritten; only invocations of the method are rewritten now. Recursive calls were skipped, calls in extension form (`text.Join(a)`) mapped their arguments one parameter off, extra arguments of a `params` parameter were dropped, and only one part of a partial method changed.
- The CLI accepts a relative solution path, as its own usage examples (`roslyn-cli MySolution.sln ...`) show; it is resolved against the current directory. It used to be rejected with "Path must be a .sln, .slnx, .csproj, or standalone .cs file" even when it was one. The server, which needs an absolute path, now says that: "Path must be absolute: ...".
- `get_diagnostics` says what it reports: compiler (CS), source-generator and Razor (RZ) diagnostics plus the RMCP workspace notes. IDE/CA analyzers are not run, so a `diagnosticIds` entry such as `IDE0005` never matches; the description of the tool and of `diagnosticIds` now say so. `search_symbols`' `kindFilter` description lists `Namespace`, which it always accepted.
- `get_diagnostics` reports a diagnostic of a multi-targeted project once. Each target framework is loaded as its own project and compiled on its own, so a warning in shared code was listed, and counted in `totalCount`, once per framework. An identical diagnostic (same ID, location, message and severity) is now listed once, and for a multi-targeted project it names the frameworks that reported it in a new `targetFrameworks` field (left out of the JSON otherwise), so a diagnostic that only one framework's `#if` branch produces is still recognizable. `projectPath`, the filters and `maxResults` work on the deduplicated list.
- `find_implementations` finds the derived classes of a class and the overrides of a virtual, abstract or override member, as its description promised. It relied on Roslyn's `FindImplementationsAsync`, which only knows interfaces and their members, so for an abstract class or an abstract method it returned nothing. `transitive: false` keeps the direct subclasses and the overrides of the member itself (not overrides of those overrides); generic base classes and other projects are covered. Interfaces and interface members work as before.
- `find_references`, `find_callers`, `find_implementations`, `get_type_hierarchy` (derived types) and `get_diagnostics` return their results in a fixed order, so `maxResults` keeps the same first N on every call. Roslyn's `SymbolFinder` searches documents in parallel and compilations bind method bodies concurrently, so the order changed from one call to the next and a truncated list was a different subset each time. Results are now sorted by file, line and column (then name); `find_references` lists the declarations first, then the usages, and a position reported both as a declaration and as a usage is always the declaration; `get_diagnostics` lists the diagnostics without a file (such as `RMCP0001`/`RMCP0002`) first. `search_symbols`, `get_document_outline` and `get_symbol_info` already followed declaration order and are unchanged.
- A `sourceFile` that differs from the loaded path only in letter case works on Windows. The workspace's document lookup normalized both paths but compared them case-sensitively, so `c:\src\app\widget.cs` for `C:\src\App\Widget.cs` failed with "File not found in workspace" in every tool that takes a `sourceFile`. It now compares the way `PathResolver.PathsEqual` does (case-insensitive on Windows, case-sensitive elsewhere), as do the other comparisons of normalized document and project paths in the workspace (incremental reconciliation, the workspace cache keys) and in `get_diagnostics`.
- A file that a refactoring writes under a new name or splits off an existing file keeps that file's encoding. `rename_symbol` with `renameFile` and `move_type_to_file` wrote the result as a brand-new file, which is created as UTF-8 with BOM, so renaming the type in a BOM-less file (the `dotnet new` default) or moving a type out of one produced a file with a BOM. The commit now writes a document moved to a new path in the encoding of its old file, and `move_type_to_file`'s new file in the encoding of the file the type came from (read before anything is deleted, so this also holds when the source file is removed in the same step). `move_type_to_file` also joins the new file's usings, namespace and type with the source file's line ending instead of a hard-coded LF. Files generated from scratch (e.g. `extract_interface` with a new `targetFile`) are still written as UTF-8 with BOM.
- The CLI accepts list parameters. Every option value became a JSON string, number or boolean, so `--members`, `--fields` or `--parameters` could not be given at all, and `extract-base-class` and `change-signature`, which require one, were unusable. A value that is a JSON array or object (`--members '["Print","Other"]'`) is now passed as JSON, and the tool help marks such parameters as `string[] (JSON array)`.
- `implement_interface` (`members`), `generate_equals_hashcode` and `generate_tostring` (`fields`) reject names that match nothing with `MemberNotFound`, like `generate_constructor`, `generate_overrides` and `extract_interface` already did. Unknown names were dropped silently, so a typo generated less than asked for and still reported success. For `implement_interface` only names the interface does not have are rejected; naming a member that is already implemented stays allowed. The `generate_constructor` `members` description no longer claims that only uninitialized fields are used by default: all instance fields are, including ones with an initializer.
- `extract_base_class` no longer loses overloads. `members` selects by name, and the derived class lost every member with a selected name, but only the first overload of a method was moved into the base class; the others were deleted. All members with a selected name now move.
- `rename_symbol` with `renameFile` renames the type's own file even when the rename starts from a usage in another file. The file-name check looked at the file the symbol was found in, so renaming `Widget` from `User.cs` renamed the class but left it in `Widget.cs`. It now uses the declaration whose file is named after the type (for a partial type, the part in that file).
- `get_type_hierarchy` with `direction` `Descendants` (or `Both`) finds the descendants of an interface. Descendants came from `FindDerivedClassesAsync` alone, which finds nothing for an interface, so the list was always empty; for an interface they are now the interfaces extending it and the types implementing it (directly or indirectly).
- `diagnose` reports what it claims to. `msBuildVersion` held the SDK version (`11.0.100`) and `dotnetSdkVersion` the runtime version (`11.0.0`); they now hold the version of the MSBuild that loads projects (its `Microsoft.Build.dll`, e.g. `18.12.2`) and of the .NET SDK it belongs to, and the new `dotnetRuntimeVersion` holds the runtime's. `roslynVersion` is the package version (`5.12.0-…`) instead of the assembly version. `capabilities` lists the tools actually registered (all 41 in the server, the CLI's own names in the CLI) instead of three hard-coded names; without MSBuild only `diagnose` remains. `msBuildFound` no longer says false when MSBuildLocator finds no instance but the SDK-directory fallback would load one: `diagnose` and the workspace load now share one MSBuild selection. Workspace load failures and analyzers/generators that failed to load are reported under `warnings`, each once (a cached workspace collects its load diagnostics again whenever it re-evaluates a project). `verbose`, which was advertised but ignored, now adds `details`: every MSBuild instance found (with its MSBuild version and the selected one marked), why it was selected, the registered MSBuild path, the probed dotnet roots, and with a `solutionPath` each project's target framework, document count, analyzer/generator references (with their analyzer and generator counts) and load failures, plus the workspace load diagnostics. Without `verbose` the output stays as compact as before. The SDK fallback now also probes `DOTNET_ROOT`, the root of the running runtime, the `dotnet` host on `PATH` (following symlinks) and the usual Unix locations (`/usr/share/dotnet`, `/usr/lib/dotnet`, `/usr/local/share/dotnet`, `~/.dotnet`) besides `%ProgramFiles%\dotnet`, and orders a release above a prerelease of the same version (prerelease labels were ignored). The server and the CLI share one implementation; the CLI now also runs `roslyn-cli diagnose [--solution-path <path>] [--verbose]` without a positional solution, as its help already promised.
- `move_type_to_namespace` honors `updateFileLocation`. It was advertised, but the operation never read it and reported success without moving anything. With `updateFileLocation: true` the file now moves into the folder that matches the new namespace below the project's root namespace (`RootNamespace` `App`, namespace `App.Services.Auth` → `<projectDir>/Services/Auth/<File>.cs`), but only when that cannot change what is compiled: an SDK-style project whose default compile items are not disabled (in the project or a `Directory.Build.props`/`.targets` above it), no `<Compile>` item that matches only one of the old and new paths (an explicit `Include`, `Update` metadata, a `Remove` of the target folder), a file that declares nothing but the moved type and belongs to no other project, and a free target path. Those checks only read the project files, so after the move the project is re-evaluated with MSBuild (the same design-time load the workspace uses for incremental reconciliation), and unless MSBuild compiles the file at its new path in every target framework (an imported props file may remove the folder) the move is undone: the file goes back, folders the move created are removed, and the cached solution is restored. Whenever the file does not move, the namespace still changes and the result reports `PARTIAL_SUCCESS` with the reason (`preview` reports the project-file checks). The namespace change is written in place and the file is then moved, so it keeps its encoding; the cached solution is repointed at the new path (and folders) immediately, so the next tool call sees the file where it is on disk. The `using` the operation adds to referencing files now ends in the file's line ending instead of a hard-coded CRLF, and is followed by a blank line in a file that had no usings.
- `generate_tostring` honors `format`. The schema offered `"interpolated"` and `"stringbuilder"`, but every call generated an interpolated string. `"stringbuilder"` now builds the same text (`Person { Name = Ada, Age = 36 }`) with a `StringBuilder` local, named so that it never shadows an appended member and written as `StringBuilder` only where a `using System.Text;` allows it. Any other value is rejected with the new error `1017` (`InvalidParameterValue`) instead of being ignored. In the CLI, `--format` still selects the output format for `json`/`text` and is passed to the tool for any other value.
- Type names in generated code are no longer fully qualified when the file's usings make a shorter name available: `implement_interface` wrote `public event System.EventHandler Changed` and `int App.IRepository.this[int index]` next to `using System;` and inside `namespace App`. Generated type names (in `implement_interface`, `generate_overrides`, `extract_interface`, `encapsulate_field`, `generate_constructor`, `extract_variable` and `extract_constant`) are now marked for Roslyn's simplifier, which shortens just those names before the formatting pass. Nothing else in the file is simplified and no usings are added, so a name with no matching using stays qualified.
- `implement_interface` on a type that does not list the interface yet now adds it to the type's base list. Previously only the members were generated, so implicit stubs silently implemented nothing, explicit ones failed with CS0540, and members the type already had (that would implement the interface once it is listed) were generated a second time. The interface is now added first (after any existing base types) and the missing members are determined against the updated type. A name that resolves to a non-interface type, or to an open generic interface that would need type arguments, is rejected with `InterfaceNotFound` instead of being added.
- Generic methods generated by `implement_interface`, `generate_overrides` and `extract_interface` keep their type parameter constraints correctly. Stubs dropped every constraint, so implicitly implementing `T Clamp<T>(T value) where T : struct, IComparable<T>` produced a method that does not implement the interface member (CS0425), and an interface extracted from a constrained method no longer matched the class it came from (CS0425 once added to the base list). Interface methods and implicit implementations now restate all constraints (`class`/`class?`, `struct`, `unmanaged`, `notnull`, type constraints, `new()`, `allows ref struct`). Overrides and explicit implementations, which inherit their constraints, restate only what C# allows there: `class`/`struct`, and `default` for an unconstrained type parameter they write as `T?` (which would otherwise mean `Nullable<T>`).
- `generate_overrides`, `implement_interface`, `extract_interface` and `encapsulate_field` no longer write nullable annotations into code where they are disabled. Types were rendered with their symbol's annotations regardless of the target, so overriding `object.Equals(object?)` in a `<Nullable>disable</Nullable>` project produced `public override bool Equals(object? obj)` and `public override string? ToString()` — each a CS8632 warning — and the same happened for members of annotated interfaces. Reference types now get `?` only when nullable annotations are enabled where the code is inserted (honoring `#nullable` directives; a new file uses the project setting); in disabled code they are written without it.
- `add_missing_usings` on a file without any `using` directives now separates the new using block from the code after it with a blank line, instead of writing `using System.Collections.Generic;` directly above `namespace …`.
- Generated code uses the line ending of the file it is written into. Generated members were laid out by `NormalizeWhitespace()` (always CRLF), the formatter filled in line breaks with the platform's newline, and `add_missing_usings` ended new `using` lines with a hard-coded CRLF, so editing an LF file left it with mixed line endings — including the original line breaks next to an insertion (e.g. before the type's closing `}`) that the formatter re-laid out. The line ending is now taken from the document's existing text and applied to every line break in and around the generated code; an empty or new file (e.g. `extract_interface`/`extract_base_class` with a `targetFile`) uses the `.editorconfig` `end_of_line`, then the platform default.
- Refactorings no longer add a UTF-8 byte order mark to the files they edit. Every write went through `File.WriteAllTextAsync(..., Encoding.UTF8)`, which always emits `EF BB BF`, so any tool that touched a BOM-less file (the default for `dotnet new` and most editors) changed its encoding as a side effect, and UTF-16 files were silently converted to UTF-8. An existing file is now rewritten in the encoding its byte order mark indicates (UTF-8 without BOM when it has none); new files are still written as UTF-8 with BOM.
- Code generated by `generate_constructor`, `generate_overrides`, `generate_equals_hashcode`, `generate_tostring`, `implement_interface`, `add_null_checks`, `encapsulate_field`, `extract_interface`, `extract_base_class`, `extract_method`, `extract_constant` and `extract_variable` is now indented like the code around it. It was built with `NormalizeWhitespace()` (which lays a node out at column 0) and inserted with hard-coded line breaks, so new members, statements and types landed at column 0 with doubled blank lines, and `add_null_checks` glued its guard onto the method's opening brace; a base list added by `extract_interface`/`extract_base_class` came out as `class Person\n:IPerson{`. The inserted nodes are now marked and only they — plus the whitespace immediately around them — are run through the Roslyn formatter before the commit (honoring the project's `.editorconfig`); the rest of the file is never reformatted. `encapsulate_field` also no longer produces `privatestring Name;`: it prepended a bare `private` token, dropping both the replaced modifier's indentation and the space before the type, and now swaps the accessibility keyword in place.
- `generate_tostring` produces a `ToString()` that compiles. The interpolated string was assembled from text tokens whose source text held the literal braces unescaped, so every generated method read `$"Person { Name = {Name} }}"` and failed to compile. The braces are now escaped (`$"Person {{ Name = {Name}, Age = {Age} }}"`), and each run of literal text goes into a single token.
- `implement_interface`, `generate_overrides` and `extract_interface` now generate members that compile. **implement_interface** marked every stub `override` because interface members are abstract (CS0115), emitted each property/indexer/event accessor a second time as a standalone method (`get_Item`, `set_Name`, …), turned indexers into a property literally named `this[]`, and ignored members inherited from base interfaces (e.g. `Dispose` of an interface extending `IDisposable`). Interface members are now implemented as `public` members (or explicitly), accessors only through their property/indexer/event, indexers as real `this[...]` indexers, and members of base interfaces are included. **generate_overrides** always emitted `public` (CS0507 for a `protected` base member; a `protected internal` member from another assembly must be overridden as `protected`), dropped `ref`/`out`/`in`/`ref readonly` and `scoped` from parameters and from the `base.` call arguments, ignored `callBase` (default `true`) for properties so overrides became `return default;` plus an empty setter that silently discarded the base behaviour, emitted an indexer as a `this[]` property, emitted a member twice when an intermediate base class already overrode it (also `ToString`/`Equals`/`GetHashCode` once a base overrode them, CS0111), and offered `internal` members of other assemblies that cannot be overridden. Overrides now keep the base member's (and a restricted accessor's) accessibility, the parameter modifiers, call `base.Prop` / `base[i]` from property and indexer accessors, and each member is offered once. With `throwNotImplemented: false`, generated bodies also assign `out` parameters. **extract_interface** produced a property named `this[]` for indexers, dropped `ref`/`out`/`in` from method parameters, and copied a `private set` into the interface as a public setter the class cannot implement; it now emits real indexers, keeps parameter modifiers, includes only public accessors, and keeps `init` setters as `init`.
- `analyze_data_flow` and `analyze_control_flow` work on ordinary method bodies again. They took the first and last of *every* statement inside the line range, nested ones included, and handed those two to Roslyn — which requires siblings in one statement list. Whenever the range ended inside a nested block (a body ending in `if (x) { return y; }`) or covered a whole method (whose body block is itself a statement), the pair came from different lists, Roslyn threw, and the tool failed with error `4003`. The region is now the outermost statements fully inside the range; a whole method is analyzed through its body's statements, and a range that genuinely spans different blocks is rejected as `InvalidRegion` with a clear message. `analyze_data_flow` additionally accepts a range covering an expression-bodied member (`=> expr`) or a field/property/variable initializer, analyzing that single expression instead of reporting "No statements found".
- `extract_constant`, `extract_variable` and `extract_method` handle their selection input properly. `extract_constant` and `extract_variable` indexed the source lines without bounds checks, so a line past the end of the file (or a start after the end) surfaced as an internal `4003` error, and a column past the end of a line silently spilled into the next line; `extract_variable` also accepted an empty selection. All three now share `extract_method`'s bounds-checked position conversion and report `InvalidLineNumber` / `InvalidColumnNumber` / `InvalidSelectionRange`. `extract_variable` no longer drops the extracted expression's trivia, which fused the new name with a following keyword (`if (GetValue() is string s)` became `if (valueis string s)`; likewise `as`, `switch`, `with`). And `_` is refused as the new name for all three: a method, constant or local named `_` captures every existing discard in scope (`_ = Log(x)`, `out _`), breaking or silently changing that code.
- `sort_usings` (and `add_missing_usings`, which re-sorts the file's usings after adding) no longer moves a `global using` behind a normal `using`. The sorter ignored the `global` keyword and ordered every directive purely by group and name, so e.g. `global using App.Shared;` could end up after `using System;` — which does not compile (CS8915). Global usings are now sorted among themselves and always placed before all non-global ones.
- `add_missing_usings` and `remove_unused_usings` with `allFiles: true` now actually write their changes. Each per-file edit was pushed into the cached workspace mid-walk, and the final commit then compared that same snapshot against itself and found nothing to write: the result reported `usingDirectivesAdded`/`usingDirectivesRemoved` > 0 with an empty `filesModified`, disk was unchanged, and the cached solution kept edits that were never saved, so later tool calls worked on code that did not exist on disk. The edits are now accumulated locally and committed once, so the files are written and the cache matches disk.
- A source generator that resolves on disk but cannot actually be loaded is now reported as `RMCP0001` instead of silently contributing nothing. In the case that motivated it — an SDK's Razor generator built against a newer Roslyn than the server hosts — `GetGenerators` returns an empty array with no exception and no unresolved reference, so every `RZ` diagnostic (and every `CS` diagnostic from the generated `.g.cs`) disappeared while `get_diagnostics` reported a confident zero. Roslyn's `AnalyzerLoadFailed` event is now subscribed before compilations are materialized, and its `ReferencesNewerCompiler` code is translated into a message naming the host's Roslyn version and the fix. The Razor-generator matcher also knew only the pre-.NET 8 assembly name (`Razor.SourceGenerators`) and never recognised the .NET 8+ name `Microsoft.CodeAnalysis.Razor.Compiler`.
- Razor diagnostics work again on **SDK 10.0.400**: the host now references Roslyn 5.9.0 (was 5.6.0). The SDK's `Microsoft.CodeAnalysis.Razor.Compiler.dll` binds against `Microsoft.CodeAnalysis 5.9.0.0`, and assembly binding never rolls backward, so a 5.6.0 host loaded zero generators and every `RZ` diagnostic — along with the `CS` diagnostics from generator-emitted `.g.cs` — silently disappeared. The rule is that the host's Roslyn must be at least as new as the Roslyn shipped with the installed SDK; roll-forward keeps older SDKs working.
- Razor diagnostics work on **SDK 11.0.100**, whose Razor generator binds against `Microsoft.CodeAnalysis 5.12.0.0`; the host now references Roslyn 5.12.0 (same rule as above).
- Loading a standalone `.cs` file no longer deadlocks when the client talks to the server over synchronous pipes (e.g. Python's `subprocess`). The `git` and `dotnet restore` child processes inherited the server's stdin — the MCP protocol channel — and Git for Windows' MSYS runtime blocked at startup probing that pipe while the server had a read pending on it, so the call hung until the 5-minute load timeout. Child processes now always get their own (immediately closed) stdin. A per-step timeout is also no longer reported as cancellation of the whole load: a timed-out best-effort step is skipped, and a timed-out `run-api` falls back to the ad-hoc workspace.
- When MSBuildLocator finds no usable instance, the fallback SDK lookup compares parsed versions instead of folder names (ordinally `9.0.321` sorted above `11.0.100`) and skips SDKs newer than the host runtime, whose MSBuild it can't load.
- `rename_symbol` with `renameFile: true` no longer leaves the original file behind. The document was repointed at its new path *before* the commit, so the commit itself wrote the new file; the subsequent "does the target already exist?" check then found the operation's own output, skipped the move, and left the source file in place with the old type name. The collision check now runs before the commit, and the stale original is removed after it. A file that genuinely occupied the target path is no longer silently overwritten either — the rename is applied in place in the source file and reported as `PARTIAL_SUCCESS`, in `preview` mode too. A renamed file is now reported under `filesCreated`/`filesDeleted` rather than as a modification of a path that did not exist before the operation.
- `rename_symbol` now finds fields, events, and locals when a `line` is given without a `column`. It previously failed with "symbol not found" in that case, because the default column landed on the leading keyword (e.g. `private`) instead of the name. It now uses the same line-scanning resolution as `find_references` and `go_to_definition`.
- The server's own refactor writes (and genuine external edits shortly after) no longer trigger a full MSBuild reload. File-watcher `.cs` events are reconciled against settled disk + workspace state rather than blindly invalidating the cache.
- Cached workspace now reloads when a referenced generator assembly changes on disk, so stale source-generator output is no longer served after a `dotnet build`.
- Analyzer-reference rewrites (shadow-copy and unresolved-reference stripping) are kept in-memory and never persisted to the `.csproj` — previously every solution load rewrote project files with absolute `<Analyzer Include="…"/>` paths and mangled formatting (BOM, dropped blank lines/trailing newline).
- `get_diagnostics` no longer reports spurious Razor errors (RZ3600/RZ9985/RZ10009): the generator now receives the project's MSBuild properties (e.g. `RootNamespace`, `RazorLangVersion`) and leftover generator output is removed before re-running, so results match `dotnet build`.
- `get_diagnostics` with a `sourceFile` filter no longer silently returns an empty list when the path is equivalent but not byte-identical to the workspace's load-time-normalized document path — an 8.3 short-name component (e.g. `PROGRA~1` vs `Program Files`), mixed `/` vs `\` separators, or `..` segments. The caller's `sourceFile` is now normalized the same way as the diagnostic span paths before comparison.
- `extract_base_class` and `extract_interface` now normalize `targetFile` and `sourceFile` before deciding whether the target is a separate file, so passing the same file spelled differently (short-name component, mixed separators, `..` segments, or case) no longer incorrectly triggers the "create new file" branch. The new-vs-same-file decision is centralized in a `PathResolver.PathsEqual` helper now shared with `move_type_to_file`.
- Analyzers that MSBuild reports but the host can't load (missing DLL, target-framework mismatch) are dropped after load, fixing a `4003` error on the first tool call after an otherwise successful load.
- Cache-invalidation race (a concurrent reload could evict a freshly loaded entry), a leak that kept the old workspace and analyzer loader alive when the cache was invalidated while a tool call was still using it, and analyzer-loader locking/GC hardening.
- Responses now report timing broken out into the operation's own time (`executionTimeMs`), the workspace load time (`workspaceLoadMs`), and the combined total (`totalExecutionTimeMs`); previously the load time was lost on the way back.
- The CLI converts option values by the parameter's type instead of by how they look. A numeric- or boolean-looking value became a JSON number or boolean even for a string parameter, so `search-symbols --query 42` (or `--query true`) failed to deserialize, and a value starting with `[` became a JSON array. A string option now always stays a string; an integer option must be an integer in range (`--line abc` used to reach the tool as a string and fail there) and a boolean option `true` or `false`, otherwise the CLI exits with code 2 naming the option and the value; a list option takes a JSON array, with a clear error for anything else.
- Relative paths: the CLI resolves every path option against the current directory, not only the solution path. `--source-file Foo.cs` (the example in the CLI's own help) reached the operations as `Foo.cs`, which they refuse, since they take only absolute paths; now every string option named `*File` or `*Path` (`--source-file`, `--target-file`, `--reference-file`, `--caller-file`, `--call-file`, `--project-path`, `--solution-path`) is resolved first, as the solution path already was. The server keeps requiring absolute paths, since it does not know the client's current directory, but now refuses a relative one for any of these parameters before the workspace loads, with a message that says why (`sourceFile ('Foo.cs') must be an absolute path: the server does not know the caller's current directory, so it cannot resolve a relative path.`, code `1001`, `1002` for `targetFile`). A test keeps the rule (a string parameter named `*File` / `*Path`) in step with the schemas, which describe exactly those parameters as absolute paths; `diagnose`'s `solutionPath` description now says so too.

## [0.3.0] - 2026-02-09

### Added
- 22 new tools (41 total), organized across five categories:

  **Code Navigation (5 tools)**
  - `find_references` — find all references to a symbol across the solution
  - `go_to_definition` — navigate to the source definition of a symbol
  - `get_symbol_info` — retrieve detailed metadata for any symbol (type, accessibility, modifiers, members, docs)
  - `find_implementations` — find all implementations of an interface or abstract member
  - `search_symbols` — search for symbols by name pattern across the workspace

  **Analysis & Metrics (6 tools)**
  - `get_diagnostics` — retrieve compiler diagnostics filtered by severity and file
  - `get_code_metrics` — calculate cyclomatic complexity, lines of code, maintainability index, class coupling, and depth of inheritance
  - `analyze_control_flow` — analyze control flow for a code region (reachability, return/exit points)
  - `analyze_data_flow` — analyze data flow for a code region (reads, writes, captured variables)
  - `get_document_outline` — get a hierarchical outline of all symbols in a file
  - `get_type_hierarchy` — retrieve base types and derived classes for a type

  **Code Generation & Formatting (4 tools)**
  - `generate_equals_hashcode` — generate Equals() and GetHashCode() overrides for a type
  - `generate_tostring` — generate ToString() override for a type
  - `format_document` — format a C# file using Roslyn's built-in formatter
  - `add_null_checks` — add null-check statements for method parameters

  **Code Conversions (7 tools)**
  - `convert_expression_body` — toggle between expression body and block body for methods/properties
  - `convert_property` — convert between auto-property and full property with backing field
  - `introduce_parameter` — promote a local variable to a method parameter, updating call sites
  - `convert_foreach_linq` — convert foreach loops with Add patterns to LINQ expressions
  - `convert_to_pattern_matching` — convert if/is chains and switch statements to switch expressions
  - `convert_to_interpolated_string` — convert string.Format() and concatenation to interpolated strings
  - `find_callers` — find all callers of a symbol across the solution

- `roslyn-cli` standalone CLI tool (`RoslynMcp.Cli` package)
  - All 41 Roslyn tools accessible from the command line without an AI assistant
  - JSON output by default (pipeable to `jq`), with `--format text` for human-readable output
  - Per-tool help via `roslyn-cli <tool-name> --help`
  - Exit codes: 0=success, 1=tool error, 2=CLI error, 3=environment error

- `QueryOperationBase<TParams, TResult>` — new base class for read-only query operations
- `SymbolResolver` — general-purpose symbol resolver (position-based and name-based)
- New contract models, error codes, and enums for all 22 new tools
- New shared utilities: `MetricsCalculator`, `EqualityMemberCollector`, `NullCheckGenerator`
